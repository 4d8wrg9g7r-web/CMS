# ADR-012: `qrcode` dependency for church-app install codes

**Status:** Accepted
**Date:** 2026-08-11
**Deciders:** Founding engineering

## Context
Phase 1 of the church app (docs/domain/app.md) ships an installable web app at
/a/&lt;publicAppId&gt;. The distribution moment is physical — a QR code on the bulletin
or a lobby screen — so App Studio must render a scannable code for the install URL.
The constitution requires an ADR for any new dependency; the alternative is
hand-rolling a QR encoder (Reed-Solomon over GF(256), format-info BCH, mask
penalty scoring), which is several hundred lines of correctness-critical code that
this environment cannot verify end-to-end (no scanner available in CI).

## Decision
Add `qrcode` (^1.5, MIT, the de-facto standard Node QR encoder, no native code)
plus `@types/qrcode` as a devDependency, in the dashboard app only. Usage is
confined to server-side SVG generation in App Studio (`QRCode.toString(url,
{type: "svg"})`); nothing user-supplied reaches it except the app's own install
URL, which we construct.

## Consequences
- Codes are generated by a library exercised by millions of installs rather than
  an unverifiable in-house encoder; the scannability risk is effectively zero.
- One new runtime dependency in the dashboard app. It is not part of
  @cms/database or @cms/email, keeping the data layer dependency-free.
- If the dependency ever needs replacing, the surface is a single call site.
